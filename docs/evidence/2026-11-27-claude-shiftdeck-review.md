## 2. Feeding the display from our CDS callback

**Yes, in principle.** ShiftDeck's renderer consumes exactly one struct:

```c
struct drive_frame { uint64_t sampled_ms; int32_t rpm; int32_t kph; };   // drive_frame.h
```

It accepts a frame only if all of these hold: same size, visible,
`sampled_ms` non-decreasing and not in the future, `-1 ≤ rpm ≤ 16383`, and
`-1 ≤ kph ≤ 255`. It blanks the display once `now - sampled_ms ≥ 750 ms`
(`DRIVE_STALE_MS`). Nothing in the draw path knows about OBD.

**Smallest adapter (sketch, not an applied change).** Replace the `recv()`
loop at `shift_deck.cpp` L222–238 with a read of a latch written by our
existing CDS delegate:

```cpp
struct RpmLatch { pthread_mutex_t m; uint32_t seq; drive_frame f; };
// CDS delegate (any thread): after b58::update()/b58::read() accept a value
//   lock; f.sampled_ms = bd_mono_ms(); f.rpm = int(rpm + .5); f.kph = -1; ++seq; unlock
// invokeDataUpdate (dispatcher): lock; copy if seq changed; unlock; then the
//   existing acceptance + ease code, unchanged.
```

That is about 25 lines. The `launch`/gateway/socket members go, and
`draw()`, the assets, the XML and the actions stay unchanged.

Requirements:

- **Threading.**
  - The CDS delegate's calling thread is **unknown**. Our notes trace the
    registration path, not the dispatch context, and the manifest sets
    `asyncCallbacks=yes`.
  - Until it is shown to be the HMI dispatcher, the delegate must not call
    `updateModel`, `post` or any other `PluginApp` method. It only writes the
    latch.
  - Use `pthread_mutex` or GCC `__sync` builtins. The upstream toolchain is
    GCC 4.4.2 / gnu++98, which has no `std::atomic`.
  - Upstream's comment says posted Runnables and Messages run on the
    dispatcher thread (`bmw_list.h` L14–17). That is their claim, consistent
    with the design, but not something we have verified.
- **Units and rounding.**
  - Our notes record the native property as raw u16 ÷ 4 for valid data. That
    is the same scale and the same 16383 ceiling as OBD 0C.
  - Their worker truncates (`/4` integer). The adapter should round once and
    document it.
  - Reject NaN and negative values. Map an `{"error":N}` payload or an invalid
    status to "no new sample", never to `rpm=0`.
- **Freshness.** This is the main open issue.
  - `sampled_ms` must be the arrival time of a **new** CDS value on
    `CLOCK_MONOTONIC`, which is what `bd_mono_ms()` returns.
  - Never re-stamp a cached value. That includes the stored JSON that
    `_bindResponse` can deliver at bind, which our 20 Nov review notes is not
    proven fresh.
  - We do not know whether `engine.RPMSpeed` notifies periodically or only on
    change. If it is change-driven, a steady idle could exceed 750 ms and
    blank correctly-but-unhelpfully.
  - Set the stale window from a measured notification interval. Don't widen
    it to hide gaps.
  - Our `b58::read("rpm", timestamp, …)` has its own freshness rule. The
    adapter should apply one rule, not two different ones.
- **Delegate lifetime.**
  - The delegate holds a raw `this`. No CDS unsubscribe call appears in our
    patches.
  - Before an app with a shorter lifetime than the HMI subscribes, we need to
    know whether a removal export exists or whether `PluginApp`'s destructor
    clears the app+0x128 map.

## 3. Their `PluginApp` subclass, factory and lifecycle

**Verified facts.** These come from the static checks already recorded, plus
`readelf` today:

- The packaged ShiftDeck's 43 AppFramework and 7 CoreFramework imports match
  our installed pair by size, instruction prefix and vtable relocation slots.
  That covers the `PluginApp` primary vtable (34 slots), the `PluginApp` C1/C2
  constructors and D2 destructor, `Message` C1/D1, `post(Message, ms)`,
  `addHandler` ×2 and `updateModel(ImageID/BasicString)`.
- Its `pluginAppInfo` is 24 bytes, exported, with create at +0x10 and destroy
  at +0x14. This agrees with our HMI loader trace (26 Nov review).
- DT_NEEDED for `libShiftDeck.so`: AppFramework, CoreFramework, libm,
  libsocket, libstdc++.so.6 and libc. There are no `ios_base::Init` imports.
- `kShiftTargets` in the packaged `.so` is {5800, 6000, 6250, 6500, 6700}.
  That matches the committed source. The v0.7.18 changelog ("10 RPM steps",
  "6,000 to 8,000") is **not** reflected in the source or package at this
  commit. The audited binary is the pre-0.7.18 build.
- Toolchain: `qcc -V4.4.2,gcc_ntoarmv7le_gpp`, `-std=gnu++98`,
  `-fno-exceptions` (`build.sh` L22, L54). Ours is GCC 4.9.4 / C++11, and our
  telemetry parser throws and catches exceptions (patch 0003).

**Assumptions (theirs or ours, unproven on our car):**

- Message `0x40000003` carrying a UInt32 key dispatches to `invokeDataUpdate`
  (`boost_deck.cpp` L30–32). The `handleMessage` prefix matches our pair, but
  literal pools and callees were not compared.
- `sizeof(Message)==80` (0x50, stated for "006.016.002") is upstream's
  reconstruction. It is not confirmed for our pair.
- Same-pair stability: upstream reports HMI freezes with BoostDeck *and*
  ShiftDeck on an R19144I unit with our exact hashes, and successes elsewhere.

**Would it improve our integration?** Possibly in three narrow ways, none
proven to matter for the crash:

1. A clean, dispatcher-only model-update pattern with generation cancellation
   and idempotent `onInit` (it calls `shutdown()` first).
2. Compile-time ABI size asserts.
3. An existence proof that a plugin built with GCC 4.4.2, gnu++98, no
   exceptions and no iostream loads on some units with our framework pair.

Point 3 is a reason to *compare* toolchains in the runtime investigation. It is
not evidence that our GCC 4.9.4 build is the crash cause.

**Specific comparison I can't do without our source.** Upstream declares slot
23 `virtual bool onFinalize()`. The context lines of our patch 0005 show
`bool onInit(); void onFinalize();` in our `bmw::PluginApp` declaration.
Mangled names don't encode return type, so the audit cannot settle this. A
`void` override where the framework reads a `bool` would leave `r0`
unspecified. That is worth checking. It is not a diagnosis.

## 4. What to keep separate or defer

- **RPM transport (separate track):** the OBD worker, HSFZ, MOST/DSI and the
  diagnostic lease. Upstream itself leaves OBD 01 over MOST unverified on a
  car, and the only MOST success it reports is N20 service 22.
- **Android Auto:** keep our NbtAad plugin and its XML untouched. Put the gauge
  in a **separate** PluginApp (own manifest, connector id distinct from our 210
  and upstream's 100–120/217–218) rather than merging screens into
  `NbtAad.xml`. The open question this creates is whether a second app passes
  the same CDS availability/permission branch (400/401/402). That is
  unverified, because our admission work was for NbtAad.
- **Two subscribers:** if both NbtAad and the gauge app bind `engine.RPMSpeed`,
  only the first reaches the first-listener `_bind` path. For a clean
  experiment, have only one app subscribe.
- **Deferred entirely:** deployment and installers, the HUD, and BoostDeck
  multi-channel work.

## 6. Unresolved issues

1. The CDS delegate's thread context and callback cadence. This sets the stale
   window.
2. CDS unsubscribe/removal and delegate lifetime at `onFinalize`/destroy.
3. Whether a second, non-NbtAad app is admitted and authorised for
   `engine.RPMSpeed`.
4. Our `onFinalize` return type versus upstream's `bool`.
5. `updateModel(unsigned, bool)` exists in our installed AppFramework (needed
   only for BoostDeck).
6. Our display resolution against the 1280×480 layout.
7. The v0.7.18 ShiftDeck source is not in the tree. Don't assume the audited
   binary has the changelog's behaviour.
8. Unchanged from before: live CDS delivery, the old runtime/restart fault, and
   the loading pause.

## 8. Smallest recommended first change

1. Add `rpm_latch.h` (the latch from section 2) and a pure function that turns

2. Lift `ShiftDeck::draw`/`animatedRpm`/`digits` behind a fake `updateModel`

3. Replay synthetic and recorded-style CDS payloads (valid, `{"error":402}`,
   zero, duplicate timestamp, gap over 750 ms) and assert the model and image

   `cdsAddPropertyChangedEventHandler` and `cdsGetPropertyAsync`. Our 20 Nov
   review shows both are exported by our AppFramework, but they are not in

This touches no car, no HMI and no Android Auto path. It defines the freshness
contract we then have to measure.
